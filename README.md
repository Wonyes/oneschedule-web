# dashboard_web (ONE SCHEDULER)

개인 일정과 그룹 일정을 한 곳에서 관리하는 캘린더 웹 앱의 프론트엔드(Next.js App Router)입니다.
백엔드 API는 이 저장소에 포함되어 있지 않으며, `NEXT_PUBLIC_SERVER_IP`로 지정한 별도 서버를 호출합니다.

## 요구 사항

- Node.js 20+
- 별도로 실행 중인 백엔드 API 서버 (인증, 일정, 그룹, 공휴일/날씨 프록시 등)

## 환경 변수

`.env.local`을 만들어 아래 값을 채워주세요.

| 변수 | 설명 |
| --- | --- |
| `NEXT_PUBLIC_WEB_IP` | 프론트 자체 오리진. Playwright e2e의 `baseURL`로 사용 (예: `http://localhost:3000`) |
| `NEXT_PUBLIC_SERVER_IP` | 백엔드 API 오리진. 브라우저(axios)와 서버 컴포넌트 양쪽에서 호출하므로 공개 변수 (예: `http://localhost:8080`) |
| `KAKAO_REST_API_KEY` | 좌표→주소 변환(`/api/address`)에 쓰는 카카오 REST API 키. **서버에서만 사용**하므로 `NEXT_PUBLIC_` 접두사를 붙이지 않습니다 |
| `E2E_EMAIL` / `E2E_PASSWORD` | Playwright 로그인 테스트용 계정. 없으면 해당 테스트는 자동으로 skip됩니다 |

## 시작하기

```bash
npm install
npm run dev
```

http://localhost:3000 에서 확인합니다.

## 인증 흐름

- 로그인 성공 시 백엔드가 `access-token` 쿠키(및 refresh 쿠키)를 내려줍니다.
- `src/middleware.ts`가 보호 라우트(`/`, `/schedule`, `/group`, `/profile`) 진입 시 `access-token` 쿠키 유무를 검사하고, 없으면 리프레시를 먼저 시도한 뒤에도 실패하면 `/login`으로 리다이렉트합니다.
- 브라우저에서의 401/403은 `src/lib/api.ts`의 axios 인터셉터가 `/token-refresh`를 호출해 자동 재시도합니다.

## 디렉터리 구조 (요약)

```
src/
  app/            App Router 페이지 및 API 라우트
  components/     기능별 UI 컴포넌트 (common, home, group, schedule, ui)
  hooks/          react-query 훅(querys), zustand 스토어(stores)
  lib/            axios 인스턴스, 서버 전용 fetch, 인증 유틸
  types/          API 응답/요청 타입
  utils/          날짜·일정 계산 순수 함수
```

## 디자인 시스템 메모

색은 전부 `globals.css`의 CSS 변수로만 정의하고, 컴포넌트는 `bg-surface` / `text-foreground` 같은
시맨틱 토큰만 사용합니다. `text-white`, `text-slate-400` 같은 고정 색을 컴포넌트에 직접 쓰면
테마 전환 시 배경만 바뀌고 글자는 그대로 남아 안 보이게 되므로 쓰지 않습니다.
(예외: 배경이 테마와 무관하게 고정인 요소 — 브랜드 색 뱃지, 액센트 버튼 위의 흰 글씨 등)

표면 표현은 세 가지로만 씁니다.

| 유틸리티 | 용도 | 형태 |
| --- | --- | --- |
| `neu-flat` | 카드, 리스트 행 등 대부분의 콘텐츠 면 | 솟아오름 (`--elevation-1`) |
| `neu-float` | 더 떠 있어야 하는 요소 (브랜드 히어로 등) | 크게 솟아오름 (`--elevation-2`) |
| `neu-pressed` | 입력창, 캘린더 그리드, 토글 트랙 | 안으로 파임 (`--inset-1`) |

- 솟은 면은 **상단 1px 베벨 하이라이트 + 우하단 그림자** 조합으로 표현합니다. 이 베벨이 없으면
  같은 그림자여도 사람 눈에는 "구멍"으로 읽힙니다.
- 표면색(`--surface`)은 항상 배경(`--main-bg`)보다 한 단계 밝아야 합니다. 같거나 어두우면 파여 보입니다.
- 그림자 색은 불투명 회색 대신 반투명(`rgba`)으로 씁니다. 불투명이면 요소가 인접할 때 경계가 띠처럼 보입니다.
- 테마는 `theme` 쿠키로 저장하고 `layout.tsx`가 서버에서 읽어 `<html data-theme>`으로 렌더링합니다.
  클라이언트에서 DOM 속성만 바꾸면 `router.refresh()` 시 서버 렌더링에 덮여 사라집니다.

## 프로젝트 분석 — 남은 개선 과제

### 1. 코드 · 구조

| 항목 | 내용 | 우선순위 |
| --- | --- | --- |
| 타입 안정성 | `tsconfig.json`이 `strict: false`, `noImplicitAny: false`. 타입스크립트를 쓰면서도 런타임 오류 방지 효과가 제한적입니다. 신규 파일부터 단계적으로 켜는 것을 권장 | 높음 |
| 에러 바운더리 부재 | `app/` 전체에 `error.tsx` / `not-found.tsx` / `loading.tsx`가 하나도 없습니다. 서버 컴포넌트가 throw하면 Next.js 기본 에러 화면이 그대로 노출됩니다 | 높음 |
| 테스트 커버리지 | 소스 119개 파일 대비 단위 테스트 4개(`utils/schedule`, `time`, `weather`, `profile/page`) + e2e 1개(로그인). 인증 흐름, axios 인터셉터, 캘린더 뷰 로직에 테스트가 없습니다 | 높음 |
| 죽은 코드 | `ScheduleAddPanel.tsx`, `EventLayer.tsx`, `constant/schedule.ts`의 `dummyEvents`, `EVENT_STYLES`의 미사용 `bg`/`text` 필드, Playwright 보일러플레이트 `tests/example.spec.ts`가 어디서도 쓰이지 않습니다 | 중간 |
| 일정 겹침 계산 | `utils/schedule.ts`의 `applyLayout`이 이벤트마다 독립적으로 겹침 집합을 구해 폭을 나눕니다. A-B, B-C만 겹치고 A-C는 안 겹치는 체인에서 열 배치가 어긋날 수 있습니다 | 중간 |
| 정적 렌더링 상실 | 테마 쿠키를 루트 레이아웃에서 읽으면서 `/login`, `/sign` 등 모든 라우트가 동적 렌더링으로 바뀌었습니다. 트래픽이 커지면 PPR 도입이나 테마 적용 위치 재검토 필요 | 낮음 |
| 거대 컴포넌트 | `ui/sheet/sheet.tsx`가 455줄로 폼·참여자 선택·저장/삭제 뮤테이션을 모두 담고 있습니다 | 낮음 |
| 미들웨어 검증 | `middleware.ts`가 `access-token` 쿠키의 **존재 여부만** 확인합니다. 만료 여부는 백엔드 401 응답에 의존하므로, 만료된 쿠키를 들고 있으면 페이지 진입 후에야 실패합니다 | 낮음 |

### 2. UI · UX

| 항목 | 내용 |
| --- | --- |
| 온보딩 부재 | 회원가입 직후 "그룹 만들기 / 초대코드로 참여 / 첫 일정 등록"으로 이어지는 안내가 없어 신규 사용자가 기능을 스스로 찾아야 합니다 |
| 빈 상태(empty state) | "일정이 없습니다" 수준의 텍스트만 있고, 바로 행동으로 이어지는 CTA가 없습니다. 첫 일정 등록 버튼을 빈 상태 안에 넣는 것이 전환에 유리합니다 |
| 일정 검색 없음 | 지난 일정이나 키워드로 찾는 수단이 전혀 없습니다. 데이터가 쌓일수록 체감 문제가 커집니다 |
| 알림 없음 | 다가오는 일정을 홈에서 목록으로만 보여줍니다. 캘린더 앱의 핵심 가치인 사전 알림이 빠져 있습니다 |
| 반복 일정 없음 | 매주 회의 같은 루틴을 매번 수동 등록해야 합니다 |
| 접근성 | 아이콘 전용 버튼 일부에 `aria-label`이 없고, 키보드 포커스 링이 뉴모피즘 표면에서 잘 보이지 않습니다 |
| 모바일 검증 | 320/390px 폭에서의 오버플로 점검이 정기적으로 이뤄지지 않고 있습니다 |

### 3. 제품 · 사업

| 항목 | 내용 |
| --- | --- |
| 차별화 근거 | "개인 + 그룹 일정 통합"이 핵심 가치인데, 알림·반복 일정·외부 캘린더 연동이 없는 상태에서는 구글 캘린더 공유 대비 우위를 설명하기 어렵습니다. 리텐션을 만들 기능부터 우선 투자 필요 |

| 부가 기능 편중 | 날씨·공휴일 배너 같은 부가 기능은 있으나 핵심 스케줄링 기능이 비어 있습니다. ROI 관점에서 우선순위 재조정이 필요합니다 |
| 계측 부재 | 사용자 행동 분석(Analytics) 도구가 없어 어떤 기능이 실제로 쓰이는지 데이터로 판단할 수 없습니다 |
| 운영 모니터링 부재 | Sentry 등 에러 모니터링이 없어 배포 후 클라이언트 런타임 에러를 인지할 수단이 없습니다 |
| 강점 | 초대 코드 기반 그룹 가입 흐름(`CreateGroup`, `GroupLanding`)은 마찰이 적고 잘 만들어져 있습니다. 온보딩·공유 시나리오를 이 흐름 위에 얹는 것이 유리합니다 |

## 기능 로드맵 (백엔드 / 프론트엔드 분담)

이 저장소는 프론트엔드만 포함하므로, 아래 항목은 백엔드 API가 먼저 준비되어야 합니다.

### 1. 일정 알림 / 리마인더
- **백엔드**: 일정에 "알림 시점" 필드 추가, 알림 발송 인프라(스케줄러/큐 + FCM 또는 웹푸시), 알림 이력 조회 API
- **프론트엔드**: 웹푸시 구독 등록(Service Worker), 생성/수정 폼의 알림 시점 선택 UI, 알림함 UI

### 2. 반복 일정
- **백엔드**: 반복 규칙(RRULE 등) 저장, 반복 회차 확장(occurrence) 조회 API, "이 일정만 / 전체" 수정·삭제 로직
- **프론트엔드**: 반복 설정 UI, 캘린더 뷰의 반복 일정 렌더링, 회차별 수정 옵션 모달

### 3. 외부 캘린더 연동 (ICS)
- **백엔드**: iCalendar(.ics) export 엔드포인트, 구독용 고유 URL 발급
- **프론트엔드**: "캘린더 구독 / 내보내기" 버튼, 구독 URL 안내 UI

### 4. 다중 그룹 소속
- **백엔드**: 유저-그룹 관계 1:1 → N:M 스키마 변경, 그룹별 권한 / 전환 API
- **프론트엔드**: 그룹 전환 스위처, 뷰 상태(`useScheduleViewStore` 등)를 그룹 단위로 확장

### 5. 일정 검색 (백엔드 협의 필요)
- **백엔드**: 기간·키워드 기반 일정 검색 API (데이터가 많아지면 인덱싱 필요)
- **프론트엔드**: 검색 UI, 결과 리스트, 최근 검색어

### 6. 프론트엔드만으로 가능한 항목
- 에러 바운더리(`error.tsx`) 추가, 빈 상태 CTA 보강, 온보딩 플로우
- 죽은 코드 제거, `strict` 모드 단계 도입, 테스트 확대
- Sentry / Analytics SDK 연동 (계정 발급만 필요)
